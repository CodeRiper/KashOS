# B5 Evidence: Asynchronous Notifications & Event Signaling

## Date
2026-10-20

## Summary of Accomplishment

Milestone B5 implements seL4-compliant asynchronous notification objects (`seL4_NotificationObject`), atomic bitwise event accumulation, non-blocking polling, and event signaling.

### Key Architectural Implementations

1. **Three-State Notification State Machine (`NotificationState`)**
   - **`Idle`**: Event word is 0; no threads are waiting.
   - **`Active`**: Event word is non-zero (contains accumulated signals); no threads are waiting.
   - **`Waiting`**: Event word is 0; one or more threads are suspended waiting for a signal.

2. **Asynchronous Non-Blocking Signaling (`notification_signal`)**
   - Senders bitwise OR their capability's badge (or 1 if unbadged) into the notification event word.
   - Senders never block under any circumstance (unlike Endpoints).
   - If a thread is waiting in `Waiting` state, the signal is delivered directly to the waiting thread and the notification transitions to `Idle`.
   - If no thread is waiting, the event word accumulates (`state |= signal_badge`) and transitions to `Active`.

3. **Bitwise Event Accumulation & Demultiplexing**
   - Multiple event producers (e.g. Timer IRQ = `0x0001`, Network IRQ = `0x0002`, Disk IRQ = `0x0004`) independently signal the notification.
   - The word accumulates bitwise: `0x0001 | 0x0002 | 0x0004 = 0x0007`.
   - Consumer reads the full accumulated mask in a single atomic transaction.

4. **Non-Blocking Polling (`notification_poll`) & Blocking Wait (`notification_wait`)**
   - `notification_poll` (seL4_Poll): Atomically retrieves the accumulated event mask and clears it back to 0 without blocking.
   - `notification_wait` (seL4_Wait): If the notification is `Active`, consumes the word immediately. If `Idle`, suspends the caller into the notification's wait queue.

5. **Access Rights Enforcement (`CapRights`)**
   - `WRITE` right strictly required to call `notification_signal`.
   - `READ` right strictly required to call `notification_wait` or `notification_poll`.
   - Unauthorized calls fail with `SeL4Error::InsufficientRights`.

## Verification Evidence (Test 51)

Test T51 (`test_sel4_asynchronous_notifications_and_event_signaling`) executed and passed:
- **Initialization**: Verified master notification capability initialized in `Idle` state with 0 bits.
- **Badging**: Minted three event producers with badges `0x0001`, `0x0002`, `0x0004` and consumer capability with `READ` rights. Verified rejection of badge 0 and rejection of re-badging.
- **Event Accumulation**: Signaled sequentially from producers A, B, and C; verified word accumulated `0x0001`, `0x0003`, and `0x0007`.
- **Non-Blocking Poll**: Consumer polled slot 5, received `0x0007`, and verified word reset to 0. Second poll returned 0.
- **Blocking Wait (Receiver-First)**: Consumer blocked on Idle notification; Producer A signaled badge `0x0001`; signal was delivered directly to waiting thread and notification returned to `Idle`.
- **Active Wait**: Producer B signaled badge `0x0002`; consumer called `notification_wait` and received `0x0002` immediately.
- **Rights Enforcement**: Verified that READ-only capability rejected `notification_signal` and WRITE-only capability rejected `notification_wait` and `notification_poll`.
- **Master Unbadged Signaling**: Unbadged capability signaled badge bit 1 (`0x0001`).
