# B4 Evidence: Badged Synchronous Endpoints & Capability Routing

## Date
2026-10-20

## Summary of Accomplishment

Milestone B4 implements seL4-compliant synchronous message-passing endpoints (`seL4_EndpointObject`), unforgeable capability badging via `seL4_CNode_Mint`, and cross-protection-domain capability routing.

### Key Architectural Implementations

1. **Synchronous Rendezvous IPC (`endpoint_send`, `endpoint_recv`)**
   - Implemented three-state endpoint queue machine (`Idle`, `Send`, `Receive`).
   - Senders block on `endpoint_send` if no receiver is waiting; receivers block on `endpoint_recv` if no sender is queued.
   - When sender and receiver rendezvous, 4 message registers (`MR0..MR3`) and message metadata (`MessageInfo`) are copied directly without intermediate kernel buffering.
   - Non-blocking variants (`seL4_NBSend`, `seL4_NBRecv`) correctly return `SeL4Error::WouldBlock` and `EndpointRecvResult::NoMessage` without suspending execution.

2. **Unforgeable Client Badging (`mint_badged_endpoint`)**
   - Enforced seL4 unforgeable badging:
     - Endpoints are minted with a 64-bit badge via `mint_badged_endpoint`.
     - Re-badging of already-badged endpoints is strictly forbidden (`SeL4Error::IllegalOperation`).
     - Badges are stamped into delivered messages by the kernel; receivers cannot be spoofed by malicious callers.
     - Deriving or copying badged endpoints retains the badge immutably.

3. **seL4_Call & One-Shot Reply Protocol (`endpoint_call`, `endpoint_reply`, `endpoint_reply_recv`)**
   - `endpoint_call` atomically sends a message, blocks the caller, and mints a single-use `CapKind::Reply` capability into the receiver's designated reply slot.
   - `endpoint_reply` invokes the reply capability, wakes the caller, and immediately destroys the reply capability.
   - Replay attack protection: subsequent invocations on the consumed reply capability fail with `SeL4Error::SlotEmpty`.
   - `endpoint_reply_recv` provides the atomic reply-and-receive loop for microkernel servers.

4. **Access Rights Enforcement (`CapRights`)**
   - `WRITE` right required for `Send` and `Call`.
   - `READ` right required for `Recv` and `ReplyRecv`.
   - `GRANT_REPLY` right required for `Call`.
   - Operations on capabilities lacking necessary permissions fail immediately with `SeL4Error::InsufficientRights`.

5. **Cross-Domain Capability Routing via Endpoints**
   - Capability transfer (`transfer_cap_slot`) permits passing capabilities across protection domains.
   - Dual-GRANT invariant: Both the endpoint capability AND the transferred capability must hold `CapRights::GRANT`.
   - Transferred capability is derived into the receiver's target slot and inserted into the Capability Derivation Tree (CDT).

## Verification Evidence (Test 50)

Test T50 (`test_sel4_badged_synchronous_endpoints_and_capability_routing`) executed and passed:
- **Badging**: Verified minting with badges `0xAAAA_1111` and `0xBBBB_2222`; verified rejection of badge 0 and rejection of re-badging.
- **Non-Blocking Semantics**: Verified `WouldBlock` on empty send and `NoMessage` on empty receive.
- **Rendezvous (Sender-First)**: Sender blocked on send; receiver rendezvoused, received registers 10, 20, 30, 40 and verified unforgeable badge `0xAAAA_1111`. Endpoint returned to `Idle`.
- **Rendezvous (Receiver-First)**: Receiver blocked on receive; sender rendezvoused immediately with badge `0xBBBB_2222`. Endpoint returned to `Idle`.
- **Rights Enforcement**: Verified that READ-only endpoint rejected send; WRITE-only endpoint rejected receive.
- **seL4_Call Protocol**: Verified caller blocked; Reply capability minted in server CSpace; server replied; caller unblocked; Reply capability consumed (one-shot guarantee).
- **Capability Routing**: Transferred 4K Frame capability across domains into receiver slot 50; verified CDT hierarchy; verified rejection when `GRANT` right was absent.
