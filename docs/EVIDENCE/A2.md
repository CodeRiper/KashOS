# Evidence: Task A2 — Non-Destructive Vault Mount and Boot Checks

## Status

Revalidated on `main`. Audit date: 2026-10-23.

## Finding and correction

`Vault::open` failure in `mount_root` returns `CorruptFilesystem` without
formatting. The 2026-10-20 follow-up audit found that the T25 boot self-test
could still call `format_root` when mounting failed, and could write then
raw-tamper a test file on the persistent root disk when mounting succeeded.
T25 now only reads baseline data from an already-mounted root vault; it skips
when the vault is unavailable. `mount_root` no longer provisions directories
or files. The QEMU disk image's SHA-256 was unchanged across the final boot
smoke test.

## Automated coverage

- `kvault/tests/vault_tests.rs::open_failure_does_not_mutate_or_format_device`
  formats a test-only RAM device, attempts to open with a wrong password, and
  compares the returned device bytes with the original bytes.
- `tools/test_storage_non_destructive.py` checks that mount fallback and boot
  self-tests do not format, write files, or write raw sectors.
- GitHub Actions runs the storage regression guard.

- QEMU T0 smoke boot: reached the shell and emitted the configured markers.

  (unchanged).

QEMU boot does not establish physical disk reliability or power-loss
atomicity. The explicit installer/administrative format operation still
erases its target; installer target selection and confirmation remain
separate audit work.

The vault library deliberately destroys the header when the configured
duress credential is supplied. This is a distinct intentional destructive
feature and remains a review item for credential handling in A3; it is not a
wrong-password or automatic-format fallback.

The legacy `install-os` / `kash install os` path has also been disabled. Audit
found it wrote a synthetic MBR, deterministic pseudo-noise, and a marker to raw
sectors, while claiming that a bootable OS and encrypted vault had been
installed. The current command reports that it is disabled and performs no
disk I/O. A safe installer still needs target selection, data-loss
confirmation, credential setup, real filesystem/boot payload creation, and
power-loss recovery.

## Follow-up source and runtime revalidation (2026-10-23)

Reviewed `RootVaultFs::mount_root`, the explicit `format_root` entrypoint,
boot-time mount flow, the `unlock` path, session lock, and the storage regression
guard. The current mount path opens the existing vault and returns an error on
failure; it contains no formatter or provisioning writes. A repository search
found no call site for `format_root` outside its own wrapper/implementation and
the regression guard. The boot T25 test skips if the persistent vault is not
mounted. A failed interactive mount locks KMS and drops the mounted VFS state
under the documented KMS-then-VFS lock order. Configured duress credentials
remain intentionally destructive; this audit does not endorse or revalidate
that policy.
