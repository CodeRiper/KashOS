# Evidence: Task A11 — SMP and scheduler

## Current status (revalidated 2026-10-20)

**Status: Not implemented; AP startup is deliberately disabled.** The previous
“Completed / Verified” assessment on this page was unsupported and has been
replaced by this revalidation. CPU discovery is present, but secondary cores do
not have a safe execution context and are not started. The scheduler's host
tests for affinity do not establish hardware SMP scheduling.

## CPU-local GDT/TSS groundwork (2026-10-20)

This follow-up replaces the shared BSP GDT, TSS, and IST stacks with indexed
per-CPU storage and updates the BSP TSS stack through the current APIC ID's
discovered CPU slot. BSP CPU discovery now happens before its GDT is installed.
The secondary-CPU startup gate remains disabled.

This is only an architecture prerequisite. The IDT is still a shared table,
exception recovery/test state remains global, and the scheduler and timer path
are still global single-CPU state. The AP entry path does not call this new
initialization, and no secondary CPU was started. No SMP scheduling or userland
support is established.

## CPU-local IDT and exception state follow-up (2026-10-20)

Per-CPU interrupt state now contains a private IDT, expected-fault state,
user-fault test recovery target, and timer tick count. The BSP installs the IDT
for its discovered CPU slot. Expected kernel protection faults recover only
when vector 14 has the expected supervisor write-protection error bits and
occurs at the exact instruction address armed by the self-test; the expectation
is disarmed if that instruction returns normally. Intel's SDM identifies #PF
as vector 14 and documents its error-code bits and saved instruction pointer
(Vol. 3A, §§6.15, pp. 6-44–6-47). The current kernel does not use hardware task
switching. This avoids turning an unrelated exception into a successful
protection-test result.

Primary source:

- Intel, *64 and IA-32 Architectures Software Developer's Manual*, Vol. 3A,
  §§6.10 and 6.15: https://cdrdv2-public.intel.com/812386/253668-sdm-vol-3a.pdf

This does not start APs. The AP entry remains parked, and global task identity,
scheduler selection, and context-switch state still do not support concurrent
execution. The per-CPU IDT/fault state is groundwork only.

The source audit found that the previous AP entry enabled a periodic local
APIC timer, marked the AP online, and executed `sti` without loading an
AP-local IDT or initializing a TSS and scheduler context. Intel SDM Vol. 3A
states that the IDTR resets to base 0 and limit 0xffff, that INIT returns the
processor core to reset state, and that referencing a vector beyond the IDT
limit causes #GP. An AP timer interrupt in that state could therefore enter an
invalid exception path. This is a source-derived failure analysis; no claim is
made that every machine deterministically triple-faults.

Primary sources reviewed 2026-10-20:

- Intel, *64 and IA-32 Architectures Software Developer's Manual*, Vol. 3A,
  §§2.4.3 (IDTR reset state), 6.10 (IDT/vector lookup), and 11.4.7.3 (INIT
  reset state): https://cdrdv2-public.intel.com/812386/253668-sdm-vol-3a.pdf
- Intel manual index: https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html

## Change in this follow-up

- `boot_secondary_cores` does not prepare or start APs and reports one active
  CPU, while retaining MADT-discovered CPU count separately.
- `ap_entry` stays with interrupts disabled, does not enable the local APIC,
  and does not report the AP online.
- `apic::init_ap` is also fail-closed and performs no APIC register writes.
- The hardware report distinguishes active from discovered CPU counts.
- CI runs `tools/test_smp_aps_fail_closed.py` to guard these properties.

## T0 smoke-test timeout and live-marker correction (2026-10-20)

The T0 smoke test could block forever in `proc.stdout.readline()`, so its
60-second timeout was not effective when QEMU stopped producing serial output.
Its assertions also required T40/T44 labels that were absent from the boot
output and checked an outdated vault prompt. On this Windows host, CP1252
console output raised `UnicodeEncodeError` on boot text containing unsupported
characters. The test now reads serial output on a daemon thread and polls a
queue with a bounded timeout, replaces unsupported console characters, and
checks boot markers emitted by the current kernel. CI includes a baseline-aware
source guard for these requirements.
