# Evidence: Task A11 — SMP and scheduler

## Current status (revalidated 2026-10-20)

**Status: Not implemented; AP startup is deliberately disabled.** The previous
“Completed / Verified” assessment on this page was unsupported and has been
replaced by this revalidation. CPU discovery is present, but secondary cores do
not have a safe execution context and are not started. The scheduler's host
tests for affinity do not establish hardware SMP scheduling.

The source audit found that the previous AP entry enabled a periodic local
APIC timer, marked the AP online, and executed `sti` without loading an
AP-local IDT or initializing a TSS and scheduler context. Intel SDM Vol. 3A
states that the IDTR resets to base 0 and limit 0xffff, that INIT returns the
processor core to reset state, and that referencing a vector beyond the IDT
limit causes #GP. An AP timer interrupt in that state could therefore enter an
invalid exception path. This is a source-derived failure analysis; no claim is
made that every machine deterministically triple-faults.

Primary sources reviewed 2026-10-20:

- Intel, *64 and IA-32 Architectures Software Developer's Manual*, Vol. 3A,
  §§2.4.3 (IDTR reset state), 6.10 (IDT/vector lookup), and 11.4.7.3 (INIT
  reset state): https://cdrdv2-public.intel.com/812386/253668-sdm-vol-3a.pdf
- Intel manual index: https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html

## Change in this follow-up

- `boot_secondary_cores` does not prepare or start APs and reports one active
  CPU, while retaining MADT-discovered CPU count separately.
- `ap_entry` stays with interrupts disabled, does not enable the local APIC,
  and does not report the AP online.
- `apic::init_ap` is also fail-closed and performs no APIC register writes.
- The hardware report distinguishes active from discovered CPU counts.
- CI runs `tools/test_smp_aps_fail_closed.py` to guard these properties.
