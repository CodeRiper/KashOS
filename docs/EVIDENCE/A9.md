# Evidence: Task A9 — Intel VT-d and PCIe ACS

## Status

Needs revalidation. Audit date: 2026-10-20. The previous “Completed / Verified”
label confused an in-memory page-table model with DMA enforcement by hardware.
VT-d activation and ACS verification now fail closed; hardware DMA containment is
not implemented.

## Research sources

- [Intel VT-d Architecture Specification, Revision 5.0](https://cdrdv2-public.intel.com/831418/vt-directed-io-spec.pdf), consulted 2026-10-20. Hardware root/context tables and second-level tables must be device-visible memory, and activation involves the register protocol and invalidation requirements defined by the spec.
- [UEFI Forum ACPI document index: DMAR table](https://uefi.org/acpi), consulted 2026-10-20. DMAR describes remapping hardware and device scopes; locating the table alone does not mean translations are active.
- [PCI-SIG ACS Enhanced Capabilities ECN](https://pcisig.com/PCI%20Express/ECN/Base/ACSEnhancedCapabilities), consulted 2026-10-20. ACS is a PCIe extended capability whose controls must be read and configured; a PCIe capability alone does not prove ACS isolation.

## Source findings

- `khal/src/vtd.rs` stores page-table contents in `BTreeMap`s and allocates
  synthetic frame numbers beginning at `0x4000_0000`. These arrays are not the
  physical tables consumed by VT-d hardware.
- `IntelVtdUnit::init_hardware` previously programmed an address derived from a
  Rust array pointer without a physical allocator, register mapping, complete
  timeout handling, or context-table programming. `isolate_device` only changed
  software data structures; it did not populate hardware context entries.
- `IommuController::enable_dma_remapping` returned success without enabling
  remapping. The ACS probe returned preset hardened flags after seeing a basic
  PCIe capability, without parsing the ACS extended capability or controls.
- Selftest T19 exercised the software model but described it as hardware DMA
  containment. The shell also printed hardware containment claims.
- ACPI DMAR discovery and software model tests do not prove VT-d is active or
  that any DMA request is constrained.

## Fail-closed changes

- Hardware init returns an error before MMIO access and cannot set `is_enabled`.
- The exported `init_vtd` records the DMAR discovery result but creates no active
  units, sets status to Stub, and makes no PCI scan or VT-d register write.
- The IOMMU controller rejects enable, map and unmap calls while inactive; ACS
  reports unavailable with all controls false.
- The hardware tier requires at least one active VT-d unit. T19 now separately
  checks that hardware activation fails and tests only `SlptPageTable` as a
  software policy model. The shell says DMA containment is unavailable.
- `tools/test_vtd_fail_closed.py` is run by CI; F8's source check now detects the
  synthetic allocator that remains in the software model.

## Verification limits

The fail-closed guard and release kernel build verify the unsupported hardware
path stays inactive. The tests do not exercise an Intel VT-d unit, physical
page-table programming, IOTLB/context invalidation, interrupt remapping, PCIe
ACS, or DMA fault records. A9 remains incomplete until those paths are
implemented against hardware-visible memory and tested with QEMU IOMMU profiles
and physical devices.
