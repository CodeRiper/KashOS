# Evidence: Task A3 — Key Management Re-Audit

## Status

Needs revalidation. Audit date: 2026-10-20. The previous “Completed / Verified”
label was not supported by current source and has been removed.

## Findings

- `kernel/src/kms.rs` defines `DEFAULT_BOOTSTRAP_PASSPHRASE` as a public,
  fixed string. `init()` derives the active key from that value without user
  input, so installations using this path share a predictable credential.
- `SYSTEM_KDF_SALT` is compiled into the kernel. `kvault::derive_key` uses
  HKDF-SHA256 directly on the passphrase, not a password-hardening KDF.
- `sealed_handle` starts at zero in memory and is not loaded from persistent
  TPM state. The apparent unseal-on-boot path therefore has no persistent
  provisioning source in this implementation.
- `unlock_with_passphrase` derives and installs a key but does not enroll or
  validate a TPM-protected key. Existing disks may rely on the fixed legacy
  bootstrap-derived credential, so changing this behavior needs a recovery and
  migration design before implementation.

## Required work before A3 can be marked complete

Design and test user credential enrollment and unlock, a salted password KDF
with documented parameters, persistent TPM object creation/recovery, hardware
failure behavior, lock/unlock lifecycle, and migration from legacy volumes.
Never silently reformat or make old encrypted data unrecoverable during this
change. A real GUI or a protected non-echoing credential path is also needed;
the current unlock API alone is not a user-facing credential flow.

## Verification

Source review was performed in `kernel/src/kms.rs` and `kvault/src/crypto.rs`
on 2026-10-20. No A3 implementation change is claimed in this revision.
