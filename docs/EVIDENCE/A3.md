# Evidence: Task A3 — Key Management Re-Audit

## Status

Needs revalidation. Audit date: 2026-10-20. The previous “Completed / Verified”
label was not supported by current source and has been removed. This revision
removes automatic unlock and adds an explicit hidden console unlock path; the
full persistent TPM hierarchy and GUI credential flow remain unfinished.

## Findings

- Before this revision, `kernel/src/kms.rs` defined
  `DEFAULT_BOOTSTRAP_PASSPHRASE` as a public fixed string and `init()` derived
  the active key without user input. Boot now starts locked; unlock requires
  a passphrase entered at a hidden console prompt.
- The KMS transform still uses a compiled-in salt and HKDF-SHA256. The
  encrypted volume then applies Argon2id using its own per-volume stored salt
  and parameters. A separate, versioned KMS password KDF and enrollment format
  are not implemented.
- Vault unlock now validates the Argon2 memory cost before allocating. Normal
  `Vault::open` is capped at 256 MiB; the kernel uses the largest contiguous
  free heap block less a 16 MiB reserve. An explicit-budget API is available
  for offline recovery up to 2 GiB when the caller has measured sufficient
  memory. This prevents hostile headers from requesting the previous 4 GiB
  maximum, but does not implement KDF versioning or credential enrollment.
- `sealed_handle` starts at zero in memory and is not loaded from persistent
  TPM state. The apparent unseal-on-boot path therefore had no persistent
  provisioning source. The KMS no longer attempts this path or claims a TPM
  sealed key is active.
- The old source's public development credential was
  `KashOS-Sovereign-Node-2026`. Existing development volumes formatted with
  that credential remain accessible by entering it manually, but it is public
  and provides no meaningful secrecy. Do not use it for new data.

### Follow-up: weak KDF profiles on new volumes

Source audit found that `KdfParams::validate_with_memory_limit` accepted
8 KiB, and `Vault::format` used that structural check before writing a volume.
The 64 KiB `TEST_ONLY_INSECURE_FAST` profile also appeared in the kernel boot
self-test. A new regression assertion failed before the fix because the 8 KiB
profile was accepted. This is distinct from the KDF memory-exhaustion guard:
it allowed new persistent volumes with an unsuitable offline-guessing cost.

New volume formatting now requires at least the OWASP Argon2id floor of
19 MiB, t=2, p=1. Older low-cost volumes remain readable for data recovery. The
fast fixture is compiled only under `test-fast-kdf` in debug builds, and the
kernel self-test uses the supported 19 MiB profile. The legacy constant that
claimed 32 passes was also corrected to 16, matching the accepted parameter
range.

Research (2026-10-20): the [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
sets 19 MiB, t=2, p=1 as the Argon2id minimum; [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)
recommends 64 MiB, t=3, p=4 for memory-constrained environments. KashOS keeps
the OWASP floor for low-memory new volumes and permits stronger supported
profiles. These parameter recommendations do not establish the vault's overall
security level or the entropy of a selected passphrase.

## Required work before A3 can be marked complete

Design and test user credential enrollment, a versioned password KDF with
documented parameters, persistent TPM object creation/recovery, hardware
failure behavior, lock/unlock lifecycle, and migration from legacy volumes.
Never silently reformat or make old encrypted data unrecoverable during this
change. The current credential path is console-only; a protected GUI flow is
still needed. The TPM driver's existing seal/unseal self-tests use an
in-memory model and do not verify TPM hardware commands.

### Session-lock key residency follow-up

Source review found that KMS scrubbing alone left the mounted root `Vault`
usable with derived keys still resident. The session-lock API now drops the
mounted vault and marks the root unavailable; the KMS boot-lock guard checks
both operations and their lock ordering. This ensures the wrapper API's future
lock callers cannot leave the root mounted. The current GUI does not call this
kernel API, and already-returned plaintext buffers are outside this boundary.
The primitive and its source guard do not establish full-session zeroization.
