# Evidence: Task A10 — User-Space Services and Ring 3 Transition

## Status

Needs revalidation; the planned service migration is incomplete. Audit date:
2026-10-20.

## Finding

Ring 3 entry, syscall, and fault-handling mechanisms are exercised by boot
self-tests using hand-built test programs. The normal boot path does not spawn
the desktop, settings UI, or console as user processes. `session.rs` invokes the
desktop and shell directly while still in Ring 0. The old A10 evidence marked
this task complete because it moved calls from `main.rs` into a module and
treated synthetic capabilities as a user session; that conclusion was wrong.

The process launcher and user-mode mechanisms do not demonstrate that the
ordinary services run in Ring 3. `UserSession::setup_capabilities` previously installed
fabricated addresses and broad model capabilities without creating a process;
that setup has been removed. The `run-user` shell command now reports the
missing boot integration rather than printing a successful transition.

## Changes in this revalidation

- Renamed the boot handoff to `launch_kernel_resident_session` and made its
  logs state that the desktop and console remain in Ring 0.
- Removed the fake session CSpace setup and associated claim that a user
  session had been spawned.
- Changed the Ring 3 status from Real to Partial after T13, since T13 exercises
  a test process while normal user services are not connected.
- Corrected the settings/status output, README, claims table, and master-plan
  finding. Updated the ground-truth verifier to inspect the actual session
  call sites instead of only searching `main.rs`.
- Added a CI regression guard for the kernel-resident session and its status
  labels.
- Follow-up source review found process CSpaces were indexed by slot at spawn
  but by `PID % MAX_PROCESSES` in syscalls and cleanup. It also found spawn
  installed fabricated untyped/frame capabilities with `Rights::ALL`. The
  process authority follow-up resolves PIDs through the process table, starts
  user CSpaces empty, and rejects invalid rights masks instead of defaulting
  them to all rights.

## Verification

The fail-closed claim guard verifies that the ordinary desktop and console are
identified as kernel-resident, fake session capabilities are absent, the
status remains Partial, and the verifier detects the current F10 condition.
Build and boot tests check that this honesty correction preserves the existing
prototype UI boot path. Those tests do not establish process isolation for the
desktop, shell, settings, browser, file service, or device drivers.

## Remaining work

A10 remains open. It requires a real user-space init/session manager, verified
physical page and stack allocation, process address spaces mapped from user
ELF images, syscall/IPC authority tied to per-process capabilities, fault and
restart containment, and migration of the desktop and shell out of Ring 0.
Until those pieces are implemented and integration-tested, the system is a
Ring-0 UI prototype with separately tested Ring 3 mechanisms.

The syscall entry still uses a single global kernel stack, so concurrent
multi-core user-process syscall safety is not established. That must be fixed
before general SMP userland is enabled.

## Follow-up source audit (2026-10-20)

After PR #9, source search found additional identifier-to-slot assumptions not
covered by `tools/test_process_authority_fail_closed.py`: driver capability
lookups in `kernel/src/driver.rs` still calculate `pid % MAX_PROCESSES`; IPC
capability lookups and scheduler wakeups in `kernel/src/ipc.rs` do the same;
IPC endpoint selection calculates `endpoint_id % MAX_ENDPOINTS`. These paths
can alias identifiers to unrelated table entries. They remain uncorrected and
unverified; add regression checks for collisions and unknown IDs before
replacing the arithmetic with live-table resolution.

The process-authority follow-up passed seven source regression checks, the
release kernel build, and the T0 QEMU smoke test. T13 exercised a process whose
PID modulo differs from its process-table slot and confirmed its CSpace starts
empty. This does not establish concurrent syscall safety or complete the
desktop/shell migration.

## Identifier-resolution follow-up (2026-10-20)

The subsequent source audit found modulo-based PID-to-CSpace and scheduler
lookups plus modulo endpoint selection. Branch `codex/a10-identifier-resolution`
replaces those lookups with live process, scheduler, and exact endpoint-table
resolution. Duplicate active endpoint IDs and unknown IDs fail closed. Driver
service registration, capability provisioning, and restart reporting now return
unavailable rather than minting synthetic hardware capabilities or synthetic
PIDs. User-process PIDs start above the finite kernel-thread ID range.

Regression coverage now includes an unknown PID that previously aliased a
valid CSpace slot, an endpoint ID that previously aliased by `MAX_ENDPOINTS`,
duplicate live endpoint IDs, a scheduler task whose table slot differs from
its TID modulo, and the correct scheduler task waking after IPC. T18/T20 boot
self-tests now assert driver services remain unavailable rather than treating
models as hardware isolation/restarts.
