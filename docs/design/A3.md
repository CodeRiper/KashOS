# Design Note: Task A3 — Real Key Hierarchy: Passphrase First, TPM Second

## Motivation & Findings
Finding F6 documented that `kernel/src/kms.rs` generated a random 32-byte key at every boot from CSPRNG (`generating fresh master key`). Because `sealed_handle` was initialized to 0, every reboot generated a new random key and lost the previous key, completely ignoring user passphrases.

## Core Rules & Invariants
- **Rule R1 (Zero Simulation)**: The master key must be derived from genuine user credentials and hardware measurements, never throwaway random bytes on reboot.
- **Rule R2 (Fail-Closed Hardware Security)**: If an invalid passphrase is provided or PCR policy fails, KMS fails closed.
- **Passphrase First, TPM Second**:
  1. The user's passphrase is the primary root of trust (something you know).
  2. The hardware TPM 2.0 PCR seal is an optional second factor / hardware binding (something you have).
  3. If TPM 2.0 is absent (e.g. T0 Legacy hardware), the passphrase alone unlocks the system.
  4. If TPM 2.0 is present, PCR 4 (Kernel Code) & PCR 7 (Secure Boot Policy) enforce Anti-Evil Maid protection.

## Architecture Changes
1. **kernel/src/kms.rs**:
   - Eliminate random key generation at boot (`generating fresh master key`).
   - Implement deterministic passphrase derivation: `derive_master_key(passphrase, salt, info)` using HKDF-SHA256.
   - Implement `unlock_with_passphrase(passphrase)`: derives the base passphrase key and, if TPM is available, binds with the unsealed hardware secret.
   - Provide default bootstrap passphrase (`DEFAULT_BOOTSTRAP_PASSPHRASE`) for automated acceptance testing and initial provisioning.
   - Maintain volatile zeroization with `clflush` and memory fences on screen lock.
2. **kernel/src/selftest.rs**:
   - Verify deterministic passphrase derivation in Test 24.
   - Maintain TPM sealing validation in Test 27.
3. **Verification**:
   - `tools/verify_findings.py`: Finding F6 becomes ABSENT.
