# B3: Transitive Revocation & Amnesic Memory Zeroing

## Overview

Milestone B3 hardens the capability revocation subsystem to match seL4's
deterministic transitive revocation guarantees.  It ensures every descendant
capability is destroyed and all physical memory backing the revoked subtree is
zeroed before the memory can be reused.

## seL4 Revocation Semantics (Reference Manual §3.3.5)

`seL4_CNode_Revoke(cptr)`:
- Deletes every capability derived (transitively) from the target capability.
- The target capability itself is NOT deleted.
- For Untyped capabilities: resets the watermark to 0 after revoking all children,
  making the entire memory region available for retyping.
- Physical memory backing destroyed objects MUST be zeroed before any capability
  to that memory is minted again (anti-forensic / zero-remanence guarantee).

## Key Improvements in B3

### 1. Comprehensive Object Zeroing
All object types are now zeroed on revocation, not just Frame and TCB:
- Frame (4K/2M/1G), TCB, Endpoint, Notification, CNode, SchedContext,
  Reply, PageTable, VSpace, ASIDPool, IrqHandler, IOPort, IOSpace, Vcpu.

### 2. Iterative Subtree Deletion
Converted from recursive to iterative traversal using an explicit stack to
prevent kernel stack overflow on deeply nested CDT trees.

### 3. Revocation Statistics
`cnode_revoke` returns `RevocationStats { objects_destroyed, bytes_zeroed }`
for audit logging and invariant verification.

### 4. Transitive Completeness Verification
Post-revoke invariant: no slot in the CSpace has `parent == revoked_slot`
(directly or transitively).

## CDT Invariants After Revoke

After successful revocation of slot S:
- `slots[S].first_child == None`
- For all i ≠ S: if `slots[i].parent == Some(S)`, then `slots[i].cap.is_null()`
- If S is Untyped: `watermark == 0`
- All physical memory in the revoked subtree has been zeroed via the zero hook
