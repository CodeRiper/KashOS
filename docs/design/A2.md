# Design Note: Task A2 — Stop the Data-Loss Bug (Vault Open vs Format)

## Motivation & Findings
Finding F7 identified a critical data-loss vulnerability:
`mount_root` in `kernel/src/vfs.rs` treated any `Vault::open` failure (including wrong password, unsealed key mismatch, or filesystem corruption) as "no vault yet" and immediately formatted the device (`Vault::format`). Combined with F6 (ephemeral master key across reboots), real disk partitions were completely wiped upon every boot.

## Core Rules & Invariants
- **Rule R2 (Fail-Closed Hardware Security)**: When decryption or authentication fails, the storage subsystem must fail closed. It must never silently overwrite or destroy existing storage.
- **Separation of Concerns**: Mounting (`mount_root`) must strictly be a read/mount operation. Formatting (`format_root`) must strictly be an explicit administrative or installer operation.

## Architecture Changes
1. **kernel/src/vfs.rs**:
   - `mount_root()`: Attempt `Vault::open()`. If `Err(err)` occurs, log the error, refuse automatic formatting, and return `Err(VfsError::CorruptFilesystem)`.
   - `format_root()`: Implement an explicit formatting function and module-level helper `pub fn format_root(master_key: &[u8]) -> Result<(), VfsError>`. Only called during explicit OS installation or explicit administrative action.
2. **kernel/src/selftest.rs**:
   - Update Test 25 (`test_kvault_root_mount_and_bitflip_tamper_gate`) to explicitly invoke `format_root` if running in a blank/unmounted acceptance test environment.
3. **kvault/tests/vault_tests.rs**:
   - Add unit test `open_failure_does_not_mutate_device` verifying that failed `Vault::open` calls leave device contents 100% bit-for-bit unchanged.
4. **Verification**:
   - `tools/verify_findings.py`: F7 becomes ABSENT.
