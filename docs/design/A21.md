## 1. Objectives & Architectural Specification
In the KashOS Master Engineering Plan (Section 3), Task A21 completes Part A by establishing an immutable bond between real hardware probes, the status registry, codebase documentation, and continuous integration enforcement:

1. **Single Source of Truth (`kernel/src/status.rs`)**:
   - Every hardware subsystem and service status must derive strictly from runtime hardware discovery (PCI probing, ACPI parsing, CPUID feature flags, TPM 2.0 TIS MMIO handshake) and verified self-test outcomes.
   - Status values (`ComponentStatus::Real`, `Partial`, `Stub`, `NotAvailable`) must govern all service maps, shell status outputs (`status.rs`), and boot banners.
   - Never print `[OK]` unless the component has been actively probed and verified (`status == ComponentStatus::Real`).

2. **Accurate Kernel Inventory & Hard Budget Tracking (`docs/KERNEL_INVENTORY.md`)**:
   - Address Finding F14 by providing an exact, synchronized module-by-module line-of-code and unsafe block inventory.
   - Strictly verify compliance with K0 budget ceilings:
     - Kernel LoC: 24,118 <= 25,000 ceiling.
     - Unsafe blocks: 392 <= 450 ceiling.

3. **Elimination of Documentation Lags (Finding F17)**:
   - Ensure `README.md`, `manifest.toml`, and architectural documents reflect the dynamic reality reported by `StatusRegistry`.
   - Prevent misleading static claims in logs and documentation.

4. **CI Pipeline That Blocks Simulated Fakes (`.github/workflows/ci.yml`)**:
   - Enforce automated gates on every push and pull request:
     - `tools/claims_lint.py`: Fails CI if unbacked security claims, privacy-leaking local paths, or budget violations occur.
     - `tools/verify_findings.py`: Fails CI if any of the 12 Ground Truth Findings (F1–F12) regress to PRESENT.
