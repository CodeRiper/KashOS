# B4: Badged Synchronous Endpoints & Capability Routing

## Overview

Milestone B4 implements seL4-compliant synchronous message-passing endpoints
(`seL4_EndpointObject`), unforgeable capability badging, and capability routing
across isolated protection domains.

Synchronous endpoints enforce rendezvous semantics: neither sender nor receiver
can proceed until both arrive at the endpoint, transferring message registers
and capabilities in a single atomic kernel transaction without intermediate
kernel buffering.

## seL4 Architecture Reference

Reference: seL4 Reference Manual v16.0.0, §2.2 (Inter-Process Communication) & §4.2 (Endpoints).

### 1. Endpoint States

An endpoint object resides in one of three states:
- **`Idle`**: No threads are waiting.
- **`Send`**: One or more threads are blocked waiting to send a message.
- **`Receive`**: One or more threads are blocked waiting to receive a message.

### 2. Rendezvous Invariants

- **Send to Idle Endpoint**:
  - `seL4_Send`: Calling thread enqueues onto Endpoint Send queue and transitions to `BlockedOnSend`.
  - `seL4_NBSend`: Non-blocking send returns immediately (`SeL4Error::WouldBlock`) without blocking.
- **Send to Receive Endpoint**:
  - Head thread is dequeued from Receive queue.
  - Message words (`mr0..mr3`) and badge are copied directly from sender to receiver.
  - Optional capability transfer (`CapRights::GRANT` required) moves or copies capability directly between caller CSpaces.
  - Receiver transitions to `Ready` with badge delivered in message info.
- **Receive from Idle Endpoint**:
  - `seL4_Recv`: Calling thread enqueues onto Endpoint Receive queue and transitions to `BlockedOnReceive`.
  - `seL4_NBRecv`: Non-blocking receive returns immediately with label 0 / empty message.
- **Receive from Send Endpoint**:
  - Head thread is dequeued from Send queue.
  - Message words and badge are copied from sender to receiver.
  - Sender transitions to `Ready` (or blocked on Reply if `seL4_Call`).
  - Receiver transitions to `Ready` with message contents and sender badge.

### 3. Capability Badging & Compartment Routing

- An Endpoint capability has an unforgeable 64-bit `badge`.
- `badge == 0` signifies an unbadged endpoint.
- Badges can only be established via `seL4_CNode_Mint` where `badge != 0`.
- **Badge Immutability**: An already-badged endpoint capability CANNOT be re-badged. Any derivation from a badged capability retains the identical badge.
- When a client sends through a badged capability, the kernel stamps the badge onto the received message metadata (`badge` field of `MessageInfo`).
- The receiver cannot forge or manipulate the sender badge, guaranteeing secure caller identification for microkernel servers.

### 4. CapRights Access Control

- `Send` / `NBSend`: Requires `CapRights::WRITE`.
- `Recv` / `NBRecv`: Requires `CapRights::READ`.
- `Call`: Requires `CapRights::WRITE | CapRights::GRANT_REPLY`.
- `ReplyRecv`: Requires `CapRights::READ | CapRights::WRITE`.
- Capability Transfer (`cap_transfer`): Requires `CapRights::GRANT` on both endpoint capability and transferred capability.
