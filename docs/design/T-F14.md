# Design Note: T-F14 (Claims Linter & External Test Harness Skeleton)

**Task ID**: T-F14  
**Date**: 2026-10-18  
**Author**: Builder Agent  
**Guide Reference**: KashOS Build Guide v2, Section 5 (F-14), Section 7, Appendix A  

---

## 1. Objective
Establish an ungameable verification foundation before implementing any new features or claiming higher evidence levels:
1. Build `tools/claims_lint.py` to continuously enforce Appendix A of Build Guide v2 against documentation, manifests, and binaries.
2. Define the structured event protocol `KASH-EVT` in `docs/EVENTS.md`.
3. Build the host-side external test harness skeleton in `tools/harness/` that launches QEMU across the hardware CPU matrix (T0 Conroe, T2 modern) and parses structured events independently of kernel-internal assertions.
4. Integrate claims linting and harness execution into CI (`.github/workflows/ci.yml`).

---

## 2. Approach & Architecture

### A. Claims Linter (`tools/claims_lint.py`)
- **Scanned Targets**: `README.md`, `docs/**/*.md` (excluding `docs/KASHOS_BUILD_GUIDE.md` which defines the forbidden words themselves), `manifest.toml`, `Cargo.toml`.
- **Forbidden Vocabulary (without linked E6 proof in `proofs/` or E4+ evidence)**:
  - Unbacked claims of formal verification, mathematical guarantees, or unhackable systems (not implemented / unbacked).
  - Unbacked 100% completion or security claims (not done).
  - Unbacked quantum or hardware verification terms (not implemented).
  - Unbacked external references like GrapheneOS, TCG MOR, or unimplemented ciphers like XTS (not implemented).
  - Unbacked ring 3 driver claims (not implemented until F-04 real process gate passes).
  - Non-status `[OK]` prints in kernel source code.
- **Fail Conditions**:
  - Unbacked claims found.
  - Shipped ISO files unconsumed by code.
  - Presence of `"Simulating"` or `"simulated"` strings outside `cfg(test)`.

### B. Structured Event Protocol (`docs/EVENTS.md`)
- Format: Single-line JSON prefixed with `KASH-EVT `:
  ```json
  KASH-EVT {"t":1792301079,"src":"kernel","ev":"boot_ok","arch":"x86_64","cpus":1,"ram_mib":1024}
  ```
- The external harness treats only lines starting with `KASH-EVT ` as authoritative test signals; human log strings are ignored for scoring.

### C. External Test Harness (`tools/harness/runner.py`)
- Python 3 test driver running on host.
- Drives QEMU via subprocess and QMP.
- Implements tier profiles:
  - `T0`: `-cpu Conroe -smp 1 -m 1024` (and `-m 256`)
  - `T2`: `-cpu max -smp 4`
- Monitors serial output for expected events within timeout; flags forbidden panic/fault events.

## 3. Risks & Mitigations
- **Risk**: Existing documentation historically contained unbacked phrases (not done / not implemented in early prototypes). Running the strict claims linter immediately will fail until docs are cleansed.
- **Mitigation**: Stage A cleanly addresses these in subsequent cards (F-10, F-12, F-17). The linter will accurately highlight all violations so they can be rectified systematically.

## 4. Still False / Partial / Not Done Afterwards
- Kernel is not yet emitting `KASH-EVT` JSON lines (it currently prints human text). That will be wired into `kernel/src/main.rs` and `kernel/src/status.rs`.
- TPM and IOMMU hardware devices in QEMU are models, not yet real processes (addressed in Stage C/D).
- Real proof files do not exist in `proofs/` yet (Phase 10).
- CLAIMS.md still contains E2/E3 claims that need audit demotions.
